# 规则体检 —— 卖诊断,不卖规则

## 起因:一条真实的、今天就在的证据

项目所有者的配置里有 `*.myqcloud.com`,而 `bx direct add` 会拒绝它:

> ⚠ 公有云存储/CDN/开放子域平台——任何人都能注册它的子域;加进直连白名单 =
> 攻击者能用一个子域让你的真实 IP 暴露(去匿名化)。

判据是对的,而 **`policy.DirectRisk` 全仓只有一个调用点**:`internal/cli/direct.go`。
配置加载不查、`bx status` 不查、`bx doctor` 不查。

于是不管它是守卫之前加的、还是直接改 YAML 加的,**此后再也没有任何东西会提醒他**。
一条已知的去匿名化风险安静地躺在配置里,而 bx 自己有那个判据。

这不是一个孤例,是这个仓库反复出现的形状:**判据只长在一条路上,而它要保护的
状态可以从别的路进来。**

## 它不是什么

**不是规则订阅。** 规则决定「哪些流量不经过加密隧道」—— 它比 kill-switch 更接近
安全核心,让用户付费订阅一份他看不到内容的这种列表,与 bx 全部的可信度叙事冲突。
而且免费竞品(v2ray-rules-dat、Clash rule-provider)体量大几个数量级。

**卖的是「你的规则怎么样」,不是「给你一份规则」。**

## 四条检查(按可实现度排序)

### 1. 危险规则 —— 今天就能做,零新增数据

把 `policy.DirectRisk` 接到配置加载/诊断那一侧,而不只是 add 那一侧。

**这一条应当免费。** 它是安全判定,而本文档前面刚说过安全的东西不收费。
它进 spec 是因为它是这个功能的起点,不是因为它是卖点。

### 2. 死规则 —— 已经有数据

`stats` 已经按规则记 {attempts, failures}。一条 attempts 恒为 0 的用户规则,
要么域名早就不用了、要么写错了(`*.qpic.cn` 这类多半是历史遗留)。

**要小心的一点**:计数在 Core 重启时清零,所以「0 次」只说明「本次运行没命中」。
判据必须跨重启累计,否则会把刚重连的机器上每一条规则都报成死的 —— 那是这个
项目最忌讳的那种假阳性。**这是本功能最主要的新增基础设施。**

### 3. 冗余规则 —— 需要一次比对

用户手写的规则若已被内嵌 china 列表覆盖(12165 条),那条手写的没有任何作用。
判据是纯函数:拿 `route.DomainSet` 比一次。

**边界**:global 模式下 china 列表整个不生效,那时「冗余」的结论是错的。
必须读当前 mode,不能只看列表。

### 4. 缺失规则 —— 从失败反推

`direct_failed` / `proxy_failed` 已经按规则归因。反过来:某个域名反复走隧道
且慢/失败,而它看起来是国内服务 —— 提示加一条。

**这一条最容易变成噪声**,门槛要比前三条严得多,宁可不说。

## 为什么它是比「规则订阅」好得多的付费候选

| | 卖规则列表 | 卖规则诊断 |
|---|---|---|
| 可审计 | ❌ 用户看不到内容 | ✅ 全在他机器上算 |
| 能盗版 | ✅ 一份文件 | ❌ 算的是**他的**数据 |
| 免费竞品 | 一堆,且更大 | 没有 |
| 与 bx 的关系 | 外挂内容 | **只有 bx 站在数据面上** |
| 是否影响流量去向 | 是(不该收费) | 否(只给建议) |

最后两行是关键:**别人做不了这个功能**,因为数据在数据面上;而它**不决定任何
流量的去向**,只是告诉你你自己写的东西现在怎么样了 —— 所以收费不违反
「安全功能不收费」。

## 非目标

- **不自动改配置。** 它只报告。改是用户的事,而且改完要重连(bx 不热重载)。
- **不做规则市场/分享。** 那会把它推回「卖内容」。
- **不做主动探测。** 判据只用已经发生的流量(与本项目「被动观测优于主动探测」
  一致)。

## 前置工作

跨重启的累计计数(第 2 条)是唯一的硬前置。其余三条今天的数据就够。

按服务器吞吐历史(`internal/guardian/throughputhistory.go`)已经趟过一遍
「带 schema 信封 + 原子替换 + 带时间戳」的持久化,规则计数可以照抄那个形状。
