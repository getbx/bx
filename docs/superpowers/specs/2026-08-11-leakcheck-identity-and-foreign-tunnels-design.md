# 泄漏检测:先说流量归谁管,再说身份能不能被钉住

2026-08-11。前身是 `2026-08-10-leakcheck-design.md`(三条规则、一次性本地服务 + 页面)。

## 为什么要改

两件事同时推着改:

**一、用户点明了两个用法。** 「一个是 bx 开着,检测。一个是 bx 关了,但它可以作为检测其他
vpn 的工具。」第二个用法此前只在口头上存在,**代码里一处都没有体现**。

**二、用户否决了我砍掉指纹类检测的提议**,理由是「这些要的,恰恰也能反映出用户是否会被定义
身份」。这个否决是对的:一台出口在洛杉矶、时区却是 `Asia/Shanghai`、语言头 `zh-CN` 的机器,
IP 一个字节都没漏,人已经被标出来了。**「流量从哪儿出去」和「你会不会被单独认出来」是同一个
威胁的两半**,我此前把边界画在了错误的地方。

## 改之前先承认现在这版的两个真问题

**问题一:页面从头到尾没说过流量归谁管。**

`judgeWebRTC` 比较 srflx 与 HTTP 出口,相等就打绿勾「WebRTC and HTTP both left from X」。
**什么隧道都没开的时候,这个绿勾照样打**,内容是「你的真实 ISP 地址和你的真实 ISP 地址一致」。
技术上没撒谎,读起来是「我很安全」。

在「bx 关着、拿它检测别的 VPN」这个用法里,这是**方向相反**的错误 —— 与 `ipify.org` 那次
同一类:一台没有任何保护的机器被报成正常。而这一次它不是选错了域名,是**判据缺了一个前提**。

**问题二:bx 自己的 UDP 分流会被误报成泄漏。**

`udp.transport: hysteria2://另一台服务器` 时 UDP 经隧道出去、只是出口不同,srflx ≠ HTTP 出口
→ 判 `Bad`「WebRTC is bypassing the tunnel」。**零泄漏而报红。**

`udp.mode: direct-realtime` 时 UDP 真的直连,报红是对的,但措辞把用户自己的配置说成缺陷。

这正是我在判据注释里写下的那条风险(「乱喊狼来了与恒绿是同一条设计风险的两面」)—— 我防住了
强制门户返回 HTML,没防住 bx 自己的分流。

## 核心决定

### 一、先回答「谁在管这条路」,它是一切结论的挂靠点

新增纯函数 `WhoOwnsTheRoute(LocalFacts) TunnelOwner`,四态:

| | 判据 | 含义 |
|---|---|---|
| `OwnerBX` | 出口接口 == `BXTunInterface` | bx 在管 |
| `OwnerOther` | 出口接口是隧道类接口,但不是 bx 的 | **别的 VPN 在管**(用法二) |
| `OwnerNone` | 出口接口是物理接口 | 没有任何隧道 |
| `OwnerUnknown` | 出口接口没问出来 | **不是「没有隧道」** |

判据取自 `DefaultRouteV4`,而采集器问的是 `route -n get 1.1.1.1` —— 即「一个公网包实际从
哪个接口离开」。**这一点是承重的**:bx 用 split-default(`0/1`+`128/1`),真正的 `default`
路由仍指着物理网关;问 `default` 会在 bx 开着时报出物理网卡。别家 VPN 大多也用同一招,所以这
个探法对用法二一并成立。

`OwnerUnknown` 与 `OwnerNone` 必须分开,理由与 `Tristate` 那条纪律相同:**观测不到 ≠ 观测到
没有**。

### 二、没有隧道时,「没有绕过隧道」不是好消息

`OwnerNone` 时 WebRTC 那条判 `NotChecked`,措辞点明「没有隧道可绕过,你看到的就是你自己的
地址」。**绝不打绿勾。**

`OwnerUnknown` 同样不打绿勾 —— 我们连有没有隧道都没问出来,凭什么说它没被绕过。

### 三、身份类产出「矛盾」判定,不是哈希转储

browserleaks 的失败方式不是测得多,是**它只给一串哈希,从不告诉你那串哈希意味着什么**。
而 bx 手里有一样它没有的东西:**它知道出口在哪儿**。同一批数据因此应该产出:

- 时区 `Asia/Shanghai` × 出口国 `US` → **这个组合本身就是标记**
- 语言 `zh-CN` × 出口国 `US` → 同上
- ICE host candidate 是真实内网地址而非 `<uuid>.local` → **内网结构对网站可见**
- canvas 两次渲染结果相同 → **浏览器没有做任何指纹防护**

**判定的落点是「矛盾」与「有没有防护」,哈希本身进展开区。**

### 四、分区,而且各有各的总结

```
你现在的位置        中性,不打勾    出口/国家/归谁管/DNS 去向
流量路径            有好坏          WebRTC · IPv6 · DNS · 路由劫持完整性
身份可识别性        有好坏          时区 · 语言 · 内网暴露 · 指纹防护
网站看得到什么      中性,不打勾    UA/屏幕/硬件/WebGL 型号
```

**绝不合并成一个总勾。** 身份那半几乎不可能全绿(普通 Chrome 就是不防指纹),而一个永远不
全绿的总结会把整个界面训练成装饰 —— 正是原设计风险二。这次靠**分区**解,不靠删掉。

`AnomalyCount` 只数「流量路径」那一段,身份段单独计数。

## 端点

出口国从 `https://www.cloudflare.com/cdn-cgi/trace` 取。**一次请求同时给出口 IP 和国家**,
于是顺带产出一条白捡的结论:它与 `icanhazip` 对同一个出口的说法不一致时,那件事本身值得报。

**第三次踩中 china 列表,而这次是在选之前抓到的。** 拿生产用的 `route.DomainSet` + 真实内嵌
列表逐个比,结果:`ipapi.co`(我本来最可能选的)与 `ifconfig.co` **都在直连列表里**。
`ipwho.is` 当场返回 429,一并淘汰。守卫沿用 `TestPublicIPProbeDomainsAreNotChinaDirect`
的形状 —— 靠「记得选对」正是前两次失败的方式。

## 明确不做

- **不做指纹「唯一性」评分。** 没有语料库就算不出唯一性,一个编出来的百分比比不报更糟。
  只报「有没有防护」这个能观测的事实。
- **不读 bx 自己的配置。** `/etc/bx/config.yaml` 是 `0600 root`,而检测页跑在普通用户身份下。
  UDP 分流那条误报要经 Guardian `/v1/status` 出,单列一期。
- **不做 torrent / mDNS-LLMNR / NetBIOS 探测。** 前者要起 BT 客户端,后两者要发局域网包 ——
  这个功能的每一次出网都要向用户交代,而它们的收益够不上。
