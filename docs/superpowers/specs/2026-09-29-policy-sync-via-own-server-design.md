# 规则同步:经用户自己的服务器,不要账号(design)

**状态:所有者 2026-09-29 定了方向(「要同步」→ 不做账号,经自己的服务器),本文待所有者过目。**

## 一句话

Mac 把自己的分流规则加密后存到用户自己的 VPS 上;iPhone 经隧道取回、解密,用它生成 libbox 配置。
**没有账号、没有我们运营的服务器、没有中央数据库**;VPS 只存一团它读不懂的密文。

## 为什么是这个形状(被否掉的两条)

- **邮箱账号**:会产生一份「哪个邮箱在用翻墙工具、连哪台服务器」的名单 —— 对 bx 用户最危险的一类
  数据;还要一个长期运营、国内大概率被墙的站(与「不建站」的定位相反)。收费不需要它(App Store
  自己管身份),只有「卖服务器」那门生意才需要,那是另一个决定。
- **iCloud**:国区 Apple ID 的数据由云上贵州托管,高级数据保护在中国不可用 —— 等于把服务器链接交给
  国内机构保管。

## 设计

### 谁能读、谁能写:钥匙从链接里来

同一个人的 Mac 与 iPhone 用的是**同一条链接**(`bx://` 里那条 vless)。两边各自从链接派生:

```
k      = HKDF-SHA256(ikm = uuid ‖ pbk ‖ sid, salt = "bx-policy-sync", info = "v1")
blobID = hex(HMAC-SHA256(k, "blob-id"))[:32]        // 存在哪
encKey = HMAC-SHA256(k, "enc")                        // AES-256-GCM
```

- VPS 只见 blobID 与密文;**它自己也解不开**(私钥在服务端没用,钥匙要 uuid)。
- `bx server share` 给朋友的链接是**另一个 uuid** ⇒ 另一个 blobID、另一把钥匙,朋友读不到你的规则,
  也覆盖不了(不知道 blobID)。
- 换服务器/换链接 ⇒ 钥匙变了 ⇒ Mac 在新服务器上重新推一次(见下)。

### 存在 VPS 的哪:一个只听回环地址的小服务

`bx server install` 多装一个 systemd 单元 `bx-sync-store`:`bx server sync-store --listen 127.0.0.1:<port>
--dir /var/lib/bx-server/sync`。协议两条:`GET /v1/blob/<id>`、`PUT /v1/blob/<id>`(≤ 256 KB,
原子写,0600)。**不对公网开任何新端口** —— reality 的全部价值是 VPS 在外面看起来只是一台转发到
cloudflare 的机器,多一个 HTTP 口就多一个指纹。

**怎么够得着一个只听回环的服务**:经隧道。sing-box 服务端今天只有一个 direct 出站、没有路由规则,
所以隧道里要去 `127.0.0.1:<port>` 的连接,在 VPS 上就是连它自己的回环。
- **iPhone**:libbox 配置里加一条规则,把保留名 `sync.bx.internal` 送进代理出站并改写目的地为
  `127.0.0.1:<port>`(sing-box `route` 动作的 `override_address/override_port`,离线 `check` 验)。
  App 请求 `http://sync.bx.internal/v1/blob/<id>` 即可;名字不会解析到任何真地址,隧道不在就不通
  (fail-closed)。
- **Mac**:Core 已知自己隧道的 socks5 地址,推送时**显式经 socks5** 拨 `127.0.0.1:<port>` —— 不走 TUN
  (TUN 会把 127.0.0.1 当私网直连,那是本机的回环)。

### ⚠ 这条路顺带暴露了一个今天就存在的问题,必须一起修

同样的原因,**今天任何持有你链接的人(包括 `bx server share` 分出去的朋友)都能经隧道连到你 VPS 的
回环地址与内网**:本机上只听 127.0.0.1 的数据库、管理面板,云厂商的元数据地址(169.254.169.254,
里面常有实例凭据)。这是服务端配置缺一条规则,不是这次设计引入的。

修法:服务端 sing-box 加路由规则 —— **拒绝去往回环、私网、链路本地(含 169.254.169.254)的连接**,
唯一例外是 `127.0.0.1:<sync port>`。这一条**先于同步单独发**(它对今天的用户就有价值),老服务器由
`bx server install` 重装或一条 `bx server harden` 补上。

### 同步什么、谁说了算

- 内容:`{ version, updated_at, global, direct[], proxy[] }`(与 `bxkit` 的 policy 同形)。**不含链接、
  不含 bypass 网段、不含 hosts** —— 手机用不上的不上传,少一样就少一样可泄漏。
- **Mac 是真相源,手机只读**(这一期)。Mac 在规则变化后(`/v1/rules` 写盘成功、`bx direct/proxy add`)
  推一次;启动时若服务器上没有或版本旧,也推一次。
- 手机在「保护」打开时、以及保护开着每 30 分钟拉一次;拉到新版本就用它重生成配置并热重载
  (libbox `startOrReloadService`)。**拉不到就用上一次的**;从没拉到过就用默认规则,并在「保护」页说出来
  (「在用默认规则 —— 你 Mac 上的规则还没同步过来」),不假装已同步。
- Explain 用同一份(同步到的,否则默认)—— 手机上的回答与手机的实际走向永远一致。

### 失败与降级(每一种都要说得出来)

| 情形 | 手机的行为 | 屏幕上说什么 |
|---|---|---|
| 服务器还没装 sync-store(老版本) | 默认规则 | 「服务器上的 bx 太旧,不能同步规则」 |
| 还没推过 | 默认规则 | 「你 Mac 上的规则还没同步过来」 |
| 拉取失败(隧道抖动) | 上一次的 | 不说(常态抖动不当事件) |
| 解密失败(链接变了) | 上一次的 | 「规则来自另一条链接,已忽略」 |

## 分期

1. **服务端加固**(独立发):sing-box 服务端拒绝回环/私网/链路本地;`bx server harden` 给已装的机器补。
   守卫:生成的服务端配置对 `127.0.0.1`、`10.0.0.1`、`169.254.169.254` 的判定是 reject(内嵌 sing-box
   离线验)。
2. **sync-store + 纯判据**:`internal/policysync`(派生、加解密、blob 格式,纯);`bx server sync-store`。
3. **Mac 推送**:Guardian 写规则成功后推;`bx status` 报「上次同步」。
4. **iPhone 拉取**:`bxkit.PolicySyncRequest/Open`,libbox 规则里的 `sync.bx.internal`,「保护」页的那一行。

## 不做

账号、我们运营的任何服务、手机改规则回写 Mac(下一期再议)、同步链接本身、多服务器之间的同步
(每台服务器各存一份,换服务器时 Mac 重推)。
