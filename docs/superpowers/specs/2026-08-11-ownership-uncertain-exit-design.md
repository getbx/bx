# 所有权不确定:给这条 fail-closed 拒绝一个出口

## 先更正两条广为流传的说法

设计这条出口之前,先把地图查出来的两件事写清楚 —— 它们都写在 CLAUDE.md、代码注释
和用户可见文案里,而**两条都不成立**。

### 一、「`sudo bx down` 再 `sudo bx up` 能清掉它」—— 在最常见的几种形状下是假的

`Down` **从不读 `Uncertain`**,它按 `m.current.PID` 分支(`manager.go:784`、`:798`)。
于是:

| 锁存形状 | `Down` 实际做了什么 |
|---|---|
| PID==0(扫描派生:`process.go:333`/`:338`、孤儿 launching 标记)且盘上 `desired=off` | 走 `:784-794` 的提前返回(还原 DNS + 报告已停),**根本到不了 `:846` 那句 `m.current = Process{}`**。Down 报成功,锁存原样,`bx up` 照旧拒绝 |
| PID==0 且 `desired=on`(**最常见** —— 第一次失败的 `Up` 已经在 `:574-579` 把 desired 写成 on) | 落到 `:798-803` 调 `runner.Existing`,**跑的正是当初把它锁上的那次扫描**。持久条件还在就返回同一个错,`Down` 以 `core_state_read_failed` 失败,同样到不了 `:846` |
| 有真实 PID(`handleUnexpectedExit`,`:1295`) | 走到 `runner.Stop`,而 `Stop` 开头的 `verifyInstalledProcess`(`process.go:498`)对一个**从没验明身份**的进程必然失败 → `core_stop_failed`,还是到不了 `:846` |

**而且没有任何测试断言过 `Down` 会清掉这个锁存**(`manager_down_test.go` 与
`daemon_test.go` 里 `Uncertain` 零命中)。

那为什么用户报告它「有时管用」?因为 CLI 的 `bx down` 任何一步失败都会落到
`forcedMacOSTeardown`,而那条路**把 Guardian 整个 bootout 掉** —— 内存里的锁存随进程
一起消失。**真正的出路一直是「杀掉 daemon」,不是「`Down()` 清了记录」。**
把它写成后者,是一句流传了很久的错话。

### 二、「这条出路在用户可见文案里不存在」—— 也是错的

它出现在 CLI 的 `guardianCodeHints`(`client.go:271`)、菜单的切换失败提示
(`ToggleController.swift:209`)、升级中止文案(`upgraderun.go:158-163`)。
真正缺的是 **`bx status`** 与**被动状态下的菜单**(只显示 `Needs Attention`,没有码
也没有指引)。

### 三、还有一条更要命的,原本没人写下来

**锁存会升级成 `recoveryBlocked`,而那个标志挡住 `Down`。** `recoverLocked` 在
`manager.go:1070-1072` 调 `upLocked`,失败就置 `recoveryBlocked = true`;而
`recoveryBlocked` 是 `Up`、`Migrate`、**`Down`**(`:775`)与两个更新入口的第一句判断。

于是一次开机时的瞬时 `sysctl` 失败,可以把「开不了保护」变成「**关不掉保护**」——
正是 2026-08-04 那次 71 分钟事故的形状,而这个代码库为它写了三处注释。
更糟的是 `retryDaemonRecovery`(`daemon.go:727-752`)会无限重试 `Recover`,而第一次
锁上之后**每一轮都在 `manager.go:559` 短路、再也不扫描** —— 一个专门设计成不放弃的
重试循环,永远解不开一个瞬时错误。

## 证据分级:十五个产地里,只有三个真的意味着「有第二个 Core」

这是整个设计的支点。地图把 `Uncertain` 的产地分成四类:

| 类别 | 例子 | 它证明了什么 |
|---|---|---|
| (a) 扫到了像 Core 的进程 | `process.go:308`、`:338` | 一个**嫌疑**。可能是另一个终端里的 `sudo bx run`,也可能下一微秒就退出了 |
| (b) **根本扫不动** | `process.go:296`、`:333`(非 root / `sysctl` 失败 / `readable==0` 下限) | **什么都没证明。** 最容易瞬时发生的一类 |
| (c) 自己的簿记不一致 | `process.go:169`、`:437`、`:470`…**尤其 `:594`** | 与进程无关。`:594` 那处**操作系统已经确认进程没了**,失败的只是删一个 JSON 文件 |
| (d) 有个活着的、从没验明的进程 | `process.go:380`、`:458`、`:665` | **这一类才真的危险**,也是唯一带 `Resolution` 通道、能自行解开的一类 |

**十五个产地里只有三个属于 (d)。** 其余的要么是一次失败的扫描、要么是一次失败的
`unlink`、要么是一个可能早就退出了的嫌疑 —— 而它们全都锁死同一扇门。

`process.go:594` 尤其荒谬:**手里握着「安全」的证明**(OS 确认进程已消失),只因为
删不掉一个文件,就宣布所有权不确定。`/var/lib/bx` 上任何一次文件系统抖动都能锁死 daemon。

## 设计

### 支点:`Down` 今天**已经**在做「重新求证再释放」

地图第 8.2 条:唯一一种 `Down` 真能清掉锁存的情形,是 PID==0、`desired=on`、而
`runner.Existing` 这次**扫干净了** —— 清除之所以发生,正是因为一次新的扫描成功了。

**所以被官方认可的出路,语义上本来就是「重新扫描并释放」,只是绕了一整套拆除去做。**
这条设计不引入新的安全姿态,只是把同一件事写得便宜一点、并且让它真的可靠。

### 一、用户发起的 `Up`/`Migrate` 改为**重新求证**,不再无条件短路

把 `manager.go:559` 与 `:482` 那两处短路,换成一次**带证明纪律**的复查:

- **用 `confirmCoreStopped` 那套(两次扫描 + 300ms 沉降),不是裸的 `scanCores`。**
  理由在地图 8.6:`scanRunningCores` 跳过僵尸(为了崩溃重启不被刚死的 Core 卡住),
  也跳过读不出 argv 的进程 —— 一个刚被 `Terminate()` 、正在跑 defer 的子进程
  既不是僵尸也还没消失,裸扫描会给出一句假的「全清」。这正是 (d) 类里
  `cleanupFailedStart` 那个残留窗口。
- **只有「确知没有」才释放。** 扫不动、扫到了、求证本身失败 —— 三种情况一律**保持
  拒绝**,fail-closed 一步不让。这条与今天完全一致,变的只是「问不问」。
- **保留原始 cause。** 今天 `uncertainOwnership(m.current, nil)` 传的是 nil,于是
  锁存后的错误文本比第一次**更少**信息:没有 PID、没有逃生提示、也看不出是十五个
  产地里的哪一个(地图 8.4)。重新求证失败时,要带着**当初**那个 cause 一起报。

**这不是把 fail-closed 改成 fail-open。** 拒绝的判据一个字没变,变的是这个判据
**每次都重新求一遍**,而不是把第一次的结论钉死。

### 二、`Down` 必须真的清掉锁存,而且无条件

这是本期**价值最高、改动最小**的一条 —— 因为被文档、CLI、菜单、升级文案四处引用的
那条出路,今天在最常见的形状下是假的。

- `Down` 在**所有**出口(含 `:784` 那个提前返回、含各条失败路径)都要把锁存清掉。
- 清除对拆除的成败**无条件** —— 与维护挂起那一期同一条纪律:拆除即使报告失败,
  它的破坏性动作也已经做完了。
- 补上那条不存在的测试:**三种锁存形状各一个用例**,断言 `Down` 之后 `bx up` 不再
  被锁存拒绝。

### 三、锁存不得再经 `recoveryBlocked` 挡住 `Down`

`recoverLocked` 里 `upLocked` 失败就置 `recoveryBlocked = true`(`:1070-1072`)。
对**所有权不确定**这一种失败,必须走维护挂起那一期已经定下的规矩:失败照常上报、
Core 照常不起,但 `recoveryBlocked` **保持 false**。

理由与 `hold.go:158-162` 一字不差:一个会挡住 `Down` 的栅栏,本身就是事故。
「开不了」永远不许升级成「关不掉」。

### 四、`(c)` 类里「已证明安全」的那一处不再产出 uncertain

`process.go:594`(`finishExistingWatch`):OS 已确认进程消失,只是删记录失败。
这不是所有权不确定,是一次**清理失败**。改为记日志 + 照常按「进程已消失」处理 ——
与 `603b602` 当初对 `Existing()` 做的判断同源(「清不掉一个陈旧文件不等于所有权存疑,
那是给『进程还在但身份不匹配』准备的语义」)。

其余 (c) 类产地(记录读不出、状态串不认识)**保持不变**:那些确实什么都没证明。

### 五、调谐器那一侧一个字不改

循环仍然**永不**清这个锁存,仍然把它当整轮停摆的栅栏。地图第 7 条点破了一处
长期的概念混淆:既有文档反对的是**自动的后台清除者**,而不是**用户发起**的重新求证 ——
两者威胁模型不同,不该被同一句话盖掉。这条设计只动后者。

`TestReconcileOnceNeverClearsTheOwnershipUncertainLatch` 原样保留。

## 本期不做

- **不动非 darwin**。`procscan_other.go` 恒返回错误 ⇒ 恒拒绝,这是既有状态,
  且 Guardian 今天只有 darwin 实体。但要在注释里写明:谁移植 Guardian,
  重新求证对他而言是个 no-op,门仍然焊死。
- **不给调谐器执行权**(那是③b)。
- **不动 `retainUncertain` 覆盖 `m.current` 的行为**(地图 8.5:更新路径上它会顶掉
  一个健康 Core 的 `Exit` 句柄,使 `sameProcessGeneration` 此后不认那次退出)。
  那是真问题,但与本期正交,单独记一笔。

## 风险

**最大的一条:`manager_test.go:1034` 就是把「粘住」这件事编码进去的那条测试。**
`TestManagerHealthFailureUsesLiveBoundedCleanupAndBlocksRetryWhenExitUnproven`
断言第二次 `Up` 返回 `ErrProcessOwnershipUncertain` 且 `startCount() == 1`,而它的
runner **没有真实的扫描** —— 重新求证会一路走到 `runner.Existing`,可能起第二个 Core。

**这条测试必须转红,然后被改成「注入一个诚实的扫描器」而不是被删掉。**
它编码的安全属性是对的(fork 清理未证实时不许重试),错的只是它用「粘住」来表达
这个属性。改完之后它应当仍然红于「去掉重新求证的证明纪律」这个变异。

**第二条:两次扫描 + 沉降让每次被拒绝的 `Up` 多花 300ms 与约 1800 次 syscall。**
只发生在已经锁存的机器上、且由用户动作触发,可以接受;但不许把这套纪律搬进
任何按时钟驱动的路径。

**第三条:改的是准入控制。** 起第二个 Core 是这个系统里最坏的结果 —— 两个 Core
争默认路由,先退出的那个用自己的旧快照还原、掀掉另一个的劫持,于是 `bx status`
显绿而流量明文直连。任何一处放行都必须有一条专门盯着它的测试,并做变异验证。
