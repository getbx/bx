# Guardian 状态 watch —— 让指示灯跟着事实走

## 起因:一个 30 秒的谎

项目所有者敲 `bx up` / `bx down`,菜单栏图标不变;鼠标点上去,它当场变了。

不是图标坏了。链路逐行确认过:关闭档轮询间隔是 **30 秒**
(`MenuCadence.swift:13` 的 `menuPollClosedSeconds`),每一拍
`refresh` → `applyRefresh` → **`updateIcon()`**(`main.swift:295`),而 `updateIcon`
里没有任何「状态没变就跳过」的门(`main.swift:493-509`,无条件重新赋 `button.image`)。
点一下走的是 `openMenu` → `refresh(userInitiated: true)`(`main.swift:164`),立刻刷。

所以现象是**最长 30 秒的延迟**,被读成了「只有点它才变」。

而 CLI 的 `bx up`/`bx down` **没有任何通道通知菜单** —— 菜单只能轮询,
于是「指示灯什么时候说真话」由一个常量决定,而不是由事实什么时候变决定。

## 30 秒这个数字的理由已经不成立

`MenuCadence.swift:12` 写的理由是「原实现无论有没有人看都固定 5 秒 spawn 两个进程,
是纯浪费」,`Tests/MenuCadenceTests.swift:19` 还有一条守卫 `closed >= 20` 钉着它。

但**阶段①把菜单改成瘦客户端之后,轮询路径 spawn 的是 0 个进程**:`loadState`
(`main.swift:338`)只有一次 `cliIsInstalled()` 的 stat 加几次本地 unix socket 往返。
`main.swift:224` 那句「一次刷新要 spawn 四个 bx 子进程」的注释**是陈旧的**,
没跟上那次改动。

而那条守卫的措辞本身把话说反了:**菜单关着的时候,图标恰恰是唯一在被读的东西。**
用「没人在看数据行」当理由去放宽间隔,放宽掉的正是唯一有人在看的那一样。

## 为什么不是「把 30 秒改成 3 秒」

那是个两行的改动,能把延迟压到 ≤3 秒。项目所有者明确否掉了它:
**「如果不便宜的方案更优,那就不要小修小补。」**

它确实更优,而且两个轴同时更优:空闲时是**一条挂着的连接**而不是 N 次轮询,
延迟约 0 而不是一个常量。

## 它不是什么

- **不是流式事件总线。** 一次请求一次应答的长轮询,详见下文。
- **不是把轮询彻底删掉。** 兜底轮询留着,理由在「失效模式」一节 —— 那一节是这份
  设计里最不可谈判的部分。
- **不改任何流量的去向。** 全程只读:发布的是 Guardian 已经在 `/v1/status` 里
  发布的同一份 `Status`。

---

## 架构

### 一、代际号由内容派生,广播只是叫醒

单一发布点 `statusPublisher`:

```
publish(status)  →  取投影 digest  →  与上一次发布的投影比
                                      不同 ⇒ generation++ 并唤醒全部订阅者
                                      相同 ⇒ 什么都不做
```

**广播不携带任何数据,只是「现在就重算,别等下一个兵底拍」。**

这是整个设计的承重点。它意味着:

- **一次广播不可能是错的。** 漏一个广播的代价只是慢到下一个兵底拍(几秒),
  **不是永久错过**。
- **代际号只有一处会 bump,而且由内容决定。** 「新加一条改状态的路、忘了 bump」
  这件事在构造上不存在 —— 而那正是这个仓库反复栽的形状(「判据只长在一条路上,
  而它要保护的状态可以从别的路进来」)。
- 与 `internal/observe`、Core 所有权进程扫描同一条原则:**不信自己的记账,
  去问系统**。这里「问」= 重算一遍 Status 再比。

**广播点只有两个:`/v1/up` 与 `/v1/down` 的 mutation handler 落定之后。**

刻意不在 Core 意外退出、路径恢复迁移那些地方也 poke —— 那些逻辑住在 `Manager`
里,要把 publisher 穿进去,而**换来的只是把 3 秒缩短到 0**。既然按上面的设计
广播只是加速器,那两处就让它们走兵底:Core 挂了,指示灯 3 秒内变。

选 up/down 是因为那是**用户正站在旁边等反馈**的两处 —— 也正是这个 bug 的原始
现场。

**重算兵底不需要独立的 goroutine 或订阅者计数**:每个 parked 的 waiter 自己的
`select` 里带一个 3 秒分支,醒来重算一次、代际号没变就继续挂。于是「没人 watch
时开销精确为零」是构造出来的,不是维护出来的 —— 没有 ticker 的生命周期要管。

多个 waiter 各自 3 秒重算会重复计算(`compute` 里有一次 Core socket 往返),
故 `publish` 内部**合并**:距上次重算不足一个兵底间隔就直接返回缓存。
`poke` 绕过合并(真事件要立刻见效)。没有这一条,任何本地进程都能开一百条
watch 把 Core 往返放大一百倍 —— `/v1/status` 是无鉴权的读端点。

### 二、投影(digest)—— 这一节是本设计最危险的地方

`Status` 里有值是**持续在变**的:

| 字段 | 为什么易变 |
|---|---|
| `Core.LatencyMS` | 每次健康探测都抖:390 → 412 → 388 |
| `Core.FailingRules[].Attempts` / `.Failures` | 每条连接都在涨。**只零掉计数,保留 `Kind`/`Rule`** —— 「这条规则开始成片失败」是真事件,「它又多失败了 3 次」不是 |
| `Reconcile.At` | `recordReconcileRound` 是唯一写入口且**每轮都盖时间戳**,不排除它 watch 会跟着调谐环每 30 秒到 10 分钟触发。只排 `At`:`Actions`/`Held` 变了是真事件 |
| `Recovery.UpdatedAt` | 恢复进行中每次轮询都换。只排它:`State`/`Stage`/`Attempt`/`ErrorCode` 变了都是真事件,而菜单那个「Connecting — N 秒」计数器本来由它自己的本地 `toggleTicker` 驱动,不靠推送走字 |
| `StatusGeneration` 自己 | 进了投影就每次 bump 都让下一次比对不同,永久自激 |

反过来有一个**必须留在投影里、而且它证明了兵底不是可选项**的:`MaintenanceHold`
到期时从非 nil 变 nil,而**没有任何广播点会在到期那一刻 poke** —— 挂起是读取时
判过期的(沿用 `internal/toolkeys` 那个不设定时器的先例)。那一跳只能由兵底
重算发现。

**深拷贝是承重的,不是讲究。** `Status` 里 `Core`/`Reconcile` 是指针、
`FailingRules` 是切片:复制 `Status` 只复制切片头,在「副本」里把元素的计数清零
**改的是同一个底层数组**,于是真正发布出去的那份 `Status` 里计数变成 0。
一个会污染它所要度量的东西的 digest 函数,比没有 digest 更糟。
(`GuardianCapabilities()` 头上那句注释 ——「每次调用都返回新切片:共享一份底层
数组等于把一个包级可变状态发布出去」—— 说的是同一条纪律。)

**「重算整个 Status、逐字节比、变了就吐」这版实现会让 watch 几乎每次重算都触发,
比今天 30 秒轮询严格更差。** 这个坑在单测里发现不了(测试里 latency 是固定
fixture),要等真机 soak 才现形。

所以投影 = **整个 Status 减去一张明确的排除名单**,而不是一份手抄的白名单。

**默认进,方向是刻意选的,两个方向的失效模式不对称:**

- **默认进**:将来谁加一个易变字段 → watch 开始疯狂触发 → **响亮、当场可见**。
- 默认不进:将来谁加一个要紧字段 → 菜单**静默地**不再对它反应 → 安静,
  只有用户抱怨时才发现。

代价不对称,默认值站在「吵」那边(与 `Class` 零值取 `ClassRisky`、
`leakcheck.Section` 零值取 `SectionPath` 同一条纪律)。

排除名单里**每一条都要写明它为什么易变**。`StatusGeneration` 自己当然也不进
投影(否则每次 bump 都会让下一次比对不同,永久自激)。

**守卫机制**:一条**反射遍历 `Status` 全部字段**的测试 —— 逐个字段改一下,
断言「不在排除名单里的字段,改了投影必须变」。它保证的是**没有字段被静默排除**:
新加一个字段,不更新任何测试它也自动参与。

**这条守卫抓不到的那一半必须说清**:一个**新加的易变字段**会通过这条测试
(它变了、投影也变了),吵是运行期才现形的。**那只能靠真机观察**,见验收一节。

### 三、传输:长轮询,不是流式

```
GET /v1/status?wait=<generation>[&timeout=<seconds>]
```

- `current != wait` ⇒ **立刻**返回 200 + 完整 `Status`。
- 相同 ⇒ 挂住,直到:代际号变(返回新 `Status`)、超时(返回 200 + 当前
  `Status`,代际号不变 —— 这一条同时充当**通道活着的证据**)、或 Guardian 关机。
- 不带 `wait` ⇒ 立刻返回当前 `Status`,**但有两处与今天不同**:

  ① **应答多一个 `status_generation` 键** —— 客户端得先有一个代际号才能发回来。

  ② **它不再总是新算的。** 这条路也走 publisher(否则普通应答里的代际号与 watch
  那条路发布的会是两个互不相干的数,而客户端正是拿前者发回给后者的),于是它吃到
  那 3 秒合并窗口 —— 最坏返回 3 秒前的数据。
  **「行为与今天相同」这句话因此不准确,准确说法是「形状相同,最多陈旧 3 秒」。**

  为什么可以接受:**用户动作引起的变化不受影响** —— `/v1/up`、`/v1/down` 会 poke,
  poke 绕过合并,所以敲完命令再 `bx status` 拿到的是新值。落在这 3 秒窗口里的只有
  「不经广播的变化」(Core 意外退出、路径恢复迁移、挂起到期),而那几类**本来就已经
  按设计接受了最长一个兵底间隔的延迟**。换句话说这个窗口没有引入新的延迟类别,
  只是让普通 GET 与 watch 看到同一份缓存。这不是「逐字节
  相同」,是**结构上向后兼容**:Swift 侧全部字段走 `decodeIfPresent` +
  显式 `CodingKeys`(`GuardianStatus.swift`),Go 侧 `json.Decode` 默认忽略未知键,
  两边都不会因为多一个键而失败。**有一条测试专门钉这个**,因为「加个字段而已」
  正是会顺手把旧客户端弄坏的那类改动。

**为什么是 `!=` 而不是 `>`**:Guardian 重启后代际号从头开始。客户端手上是 57,
新 Guardian 在 3 —— `current > 57` 为假,请求会**永久挂住**。`!=` 立刻返回。

`!=` 剩下的那个窗口也要写下来:重启后恰好落在客户端手上那个数(小计数器,
真会发生),那次请求会挂到超时。**但超时返回的那份 `Status` 是当前真相**,
所以最坏后果是一次超时的延迟,数据不会错。加 boot id 能消掉这个窗口,
**不加**(YAGNI):兜底轮询已经覆盖它。

**为什么不用流式**:Swift 客户端是一次请求一次应答、`Darwin.read(fd)` 读到底
(`GuardianClient.swift:520`),流式要改成按行读 + 服务端 flush,两侧都要动;
而这里的事件是**人的尺度**(开关、恢复),稀少,重连成本可忽略。
长轮询那个「无变化」应答还顺手给了活性证明,流式要另造心跳。

客户端超时靠既有的 per-endpoint 表(`GuardianClient.swift:48`),
`guardianMaximumTimeout` ≈ 24 天,**没有障碍**。**客户端超时必须大于服务端挂住
上限**,否则拿到的永远是自己的超时(与 `switchServer`/`probeServers` 已经踩过并
写在注释里的是同一个坑)。

### 四、关机不许被 parked 的请求拖住

`Daemon.Shutdown`(`daemon.go:307`)是先对 mutations / recoveries / observer 调
`beginShutdown()`,**再** `d.server.Shutdown(ctx)`。而 `server.Shutdown` **会等
在跑的 handler 返回** —— 一个挂了 25 秒的 watch 会让 Guardian 关机慢 25 秒。

**升级时 Guardian 要被 bootout,而这个项目在「关机慢」上栽过**
(2026-08-04 那次 71 分钟)。所以 watch 必须挂进同一套 `beginShutdown` 范式:
收到关机信号立刻唤醒全部 parked handler、各自返回当前 `Status`。

这不是优化,是不变量:**停止路径不许因为别的事没做完而变慢或失败。**

### 五、能力声明与降级

新增 `CapabilityStatusWatch`,进 `GuardianCapabilities()`(`types.go:203`)。

菜单的引导序列:**第一次照旧拨一次不带 `wait` 的 `/v1/status`** 拿到
`Capabilities` → 声明里有 watch 就转入 watch 循环,没有就保持今天的轮询。

**绝不「试着拨一下看看」** —— 旧 Guardian 会回一份不认识 `wait` 的普通应答
(它会忽略 query 参数),客户端无从区分「立刻返回因为变了」与「这版不支持」,
于是退化成一个满速轮询。既有代码在 `/v1/rules`、`/v1/servers` 上已经采用能力
门控并写明了理由(「旧版会回 404,而那会让每一轮刷新都白拨一次 socket」),
这里取一致。

### 六、顺手修掉的浪费(它在这个设计里从可选变成承重)

今天一次刷新是 **3 次** socket 往返:`/v1/status` + `/v1/rules` + `/v1/servers`,
后两者各**读并 YAML 解析一遍 `/etc/bx/config.yaml`**。

而图标只依赖 `/v1/status`:`menuRowsNow()`(`main.swift:1257`)一个字都不碰
rules 与 servers。

**在轮询时代这是「浪费」;在 watch 时代它会变成「更糟」** —— 刷新从「每 30 秒
一次」变成「每次状态变化都有一次」,若每次都带着两份 config 解析,总开销可能
反而上升。所以:**rules 与 servers 改成打开对应子菜单/窗口时才拉。**

### 七、具体数字

这几个值互相约束,写死在这里免得实现时各猜一个:

| 值 | 取值 | 约束来自哪里 |
|---|---|---|
| 服务端挂住上限 | **25 秒** | 必须明显小于客户端超时;也是「无变化」活性证明的节拍 |
| `timeout` query 参数 | 可选,服务端**钳到 [1s, 25s]** | 客户端不许要求比 25 秒更长的挂住 —— 那会把关机延迟的上限交给客户端决定 |
| 客户端 watch 超时 | **40 秒** | 必须 > 服务端 25 秒,否则拿到的永远是自己的超时(`switchServer` 注释里已写过这个坑) |
| 重算兵底 | **3 秒**,且**只在有订阅者时才跑** | 漏一个广播的最坏延迟。没人 watch 时精确为零开销 |
| 菜单兜底轮询 | **60 秒**,watch 健康时照跑 | 「watch 已经哑了」的兜底,不是取数据的手段 |
| 菜单关闭档轮询(无 watch 时) | **保持今天的 30 秒** | 旧 Guardian 的降级路径,行为一个字不变 |

**兜底的 60 秒不因 watch 健康而放宽,也不因 watch 失败而收紧** —— 它是一个与
watch 状态无关的常量,这样「watch 哑了但我以为它好着」这种情形下它照样在跑。
一个会被 watch 的健康判断影响的兜底,在 watch 判断错的时候恰好也是坏的。

## 失效模式:为什么兜底轮询必须留着

**「指示灯不再指示」是这个组件最坏的失效模式。** 这个项目为此删掉过
`Quit Menu`(它能让用户做出「保护在跑但没有任何指示灯」的隐形状态),也为此
规定过「关不掉就不退出」。

watch 有一类失效是静默的:连接半开、Guardian 重启的窗口、客户端那条循环
自己死掉(Swift 侧的 goroutine 等价物不再返回)。这些情况下**没有任何东西会
报错**,菜单就那么停在最后一次收到的状态上,而它看起来完全正常。

所以:

- **watch 健康时也保留一条慢速兜底轮询(60 秒)。** 它的作用不是取数据,是
  「如果 watch 已经哑了,让指示灯最多哑 60 秒」。
- watch 循环必须能**自证还活着**:长轮询的「无变化」应答就是那个证据。连续
  N 次连接失败要退避重连,并且**退避期间兜底轮询照跑**。
- **绝不因为 watch 建立不起来就让菜单变哑** —— 建不起来就退回今天的轮询,
  用户什么都不会察觉,只是慢一点。

## 非目标

- **不做流式/多事件类型的总线。** 只有一个「Status 变了」这一种事件。
- **不给 watch 加过滤、订阅子集、增量 diff。** `Status` 是几 KB 的东西,
  整份发。
- **不动 Linux/Windows。** Guardian 只在 darwin 跑;Windows 托盘每 3 秒 spawn
  一次自己刷(`internal/tray`),没有这个问题,也不在本设计范围内。
- **不改任何流量决策。**

## 交付面

| 件 | 是什么 |
|---|---|
| `GET /v1/status?wait=<gen>` | 长轮询;不带 `wait` 时**形状**与今天相同,但走同一个 publisher、吃 3 秒合并窗口,不是逐字节相同(见「三、传输」一节) |
| `Status.StatusGeneration` | 内容派生的单调计数器,**刻意无 omitempty**(键缺席 = 这版没有这个概念) |
| `CapabilityStatusWatch` | 能力声明,菜单据此决定走 watch 还是轮询 |
| `bx status --watch` | 通用契约的第二个消费方,**同时是这个功能唯一的只读真机验证手段** |
| 菜单 watch 循环 | 取代关闭档轮询;rules/servers 改按需拉 |

`bx status --watch` 不是附赠品:它让项目所有者能在**不动网络、不重装菜单**的
前提下,亲眼看到「敲 `bx down` 的那一瞬间 watch 就吐了一份新 Status」。
菜单那一半的验证要重装 App,而这一条只要一个终端。

## 测试与验收

**能测的:**
- 投影:反射遍历 `Status` 全部字段,逐个改动,断言排除名单外的字段都会改变投影。
- 代际号:同一份 Status 发布两次 ⇒ 不变;只改易变字段 ⇒ 不变;改语义字段 ⇒ +1。
- 长轮询:`wait` 与当前不同 ⇒ 立刻返回;相同 ⇒ 挂住;`poke` ⇒ 醒;超时 ⇒ 返回
  当前 Status 且代际号不变;**关机 ⇒ 立刻返回**(这一条钉的是不变量,不是行为)。
- `wait` 大于当前(模拟 Guardian 重启)⇒ 立刻返回,不挂死。
- 不带 `wait` 的应答多一个 `status_generation` 键,且形状向后兼容(未知键不破坏
  解码)—— 不是逐字节相同,它吃同一个 3 秒合并窗口,见「三、传输」一节。

**测不到、必须真机看的:**
- **投影够不够安静。** 只有在真机上开着保护跑一段,数 watch 触发了几次,才知道
  排除名单是不是漏了一个易变字段。**这是本设计唯一真正的验收**,做法:
  `bx status --watch` 挂一段时间,每次吐出都打一行 —— 稳态下它应当几乎不吐。
- Guardian 关机耗时没有变长(升级路径上量一次)。
- 菜单那一半:`main.swift` 编不进 Swift 测试套件,它的接线只能靠 Go 侧读源码
  文本的守卫钉住 —— **那类守卫在这个仓库被攻破过八次**,所以菜单侧的正确性
  最终靠真机点一遍,不靠测试。

per-endpoint 超时表,四样都已经在那里。
