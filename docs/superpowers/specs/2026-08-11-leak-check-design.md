# 泄漏检测:保护关着也能用,而且不跟别的 VPN 抢活

## 为什么值得做

bx 今天是个二元产品:开着有用,关着等于不存在。而它安装在机器上、又恰好持有
**一半别人拿不到的事实**(路由归谁、v6 有没有暴露、DNS 归谁),这半份事实在保护
关着的时候一样成立。

更重要的是它与另一半的**组合**:

> 浏览器的 WebRTC 通过 STUN 拿到 srflx candidate = `1.2.3.4`,
> 而 HTTP 出口显示 = `5.6.7.8` → **WebRTC 绕过了隧道,真泄漏。**

whoer.net 这类纯网页只有右边那半(浏览器暴露给第三方的东西);一个 native app 只有
左边那半(本机路由与接口)。**两半都拿得到的位置很少,bx 恰好在那个位置上。**
这不是「也能做」,是这个功能的立身之本。

顺带解决一个真实的产品问题:bx 全量劫持默认路由,与别的 VPN 天然互斥。作为**检测
工具**它不抢任何人的活 —— 只读,别的 VPN 在跑时照样能答,而且答的正是那个 VPN
最可能漏的地方。

## 一个必须先说清楚的事实,它改掉了 WebRTC 那一项的做法

**「WebRTC 泄漏本机内网 IP」这个经典问题,浏览器自己早就修了。** Chrome/Safari/Firefox
从 2019-2020 起默认用 mDNS 混淆 host candidate —— 页面拿到的是 `<uuid>.local` 而不是
`192.168.1.50`,除非页面已获得摄像头/麦克风权限。

照那个年代的做法实现,这一项**会永远显示「无泄漏」** —— 不是因为用户安全,是因为
浏览器根本不给。**一条恒绿的检查比没有这条检查更糟**:它教会用户忽略这个界面。

**今天还有意义的是 srflx candidate** —— 向 STUN 服务器问出来的「你的公网 IP」。
在 VPN 里而 srflx 显示真实 ISP 出口,那是真泄漏,也正是 VPN 用户该担心的那一种。
代价是它需要一个 STUN 服务器,即又一个第三方。**项目所有者明确选择了做它。**

## 已定的决定(由项目所有者拍板)

| 决定 | 选择 | 代价,明确接受 |
|---|---|---|
| 检测结果是否留存 | **不留存** | 没有「这台机器什么时候漏过」的历史 —— 但那份历史本身就是敏感数据 |
| 常驻 vs 按需 | **本地项常驻、浏览器项按需**(方向);**但这一期先只做页面** | 菜单那三行暂时保持 `unknown` 不动 |
| 对别的 VPN 的判断尺度 | **只报事实,不评判对方** | 但事实必须是人话 —— 见「诚实性规则」 |
| 公网出口问谁 | **公共第三方** | 一个隐私工具在用户点「检测」时把真实 IP 递给了无关公司。缓解:只在用户显式点击时发生、页面事先明说要联系谁 |
| WebRTC | **用 STUN,测 srflx** | 又一个第三方,同一类暴露 |

## 架构:两半在 Go 里对起来,不在 JS 里

```
菜单 "Check for leaks ↗" ──┐
                           ├──> bx leakcheck(**普通用户身份**,不是 root)
CLI  bx leakcheck      ──┘         │
                                   ├─ 起一次性本地服务(127.0.0.1:随机端口 + 单次 token)
                                   ├─ 打开默认浏览器到那个 URL
                                   │
                       页面(JS)──┤  跑 ICE(STUN)/ 问公共回声 ──> POST 原始数据回本地服务
                                   │
                                   └─ Go 侧把两半对起来 ──> 页面渲染 Go 给的结论
```

三个刻意的选择:

**一、服务以普通用户身份跑,不是 root。** 需要的本地事实(`route -n get`、
`scutil --nc list`、`ifconfig`、`networksetup -getdnsservers`)全都不需要 root;
bx 自己那一半经 Guardian 的 unix socket 拿(0666,真机已验:uid 501 读 `/v1/status`
返回 200)。**一个隐私工具不该为了做体检而让 root 进程对浏览器开 HTTP。**

**二、判断逻辑在 Go 里,页面只采集和渲染。** 这个仓库的测试与变异验证覆盖不到 JS
(`apps/macos/BxMenu/Tests` 那套教训:不在 target 里的东西一次都不会跑而 CI 全绿)。
把判据放进测不到的地方,就是把这一期唯一值钱的东西放进测不到的地方。

**三、一次性。** 用户点了才起,拿到结果就关,不常驻、不后台、不留存。

**`sudo bx leakcheck` 必须被拒绝**,而不是"照跑但更强大"。以 root 跑会让那个
loopback HTTP 服务变成 root 进程的端口,把上面第一条的全部理由一笔勾销;而且它
拿到的答案不会更准 —— 需要的本地事实一个都不需要 root。拒绝时要说清换成不带 sudo
再跑,别让用户以为是权限不够。

`http://127.0.0.1` 在浏览器里算 **secure context**,所以 WebRTC 等需要安全上下文的
API 可用,不需要证书 —— 这是这条路走得通的前提,写在这里免得有人以为要搞 TLS。

## 那个本地服务的自我约束

它必须比它检测的东西更干净:

| 约束 | 挡的是什么 |
|---|---|
| 只绑 `127.0.0.1`,随机端口 | 不对局域网开口 |
| URL 带**单次随机 token**,每个请求校验 | 同机其它进程顺手读到这台机器的网络姿态 |
| 校验 `Origin`/`Host` 必须是那个精确的 loopback | **DNS rebinding** —— 否则用户访问的任何网页都能读它 |
| 拿到结果即关,另设硬超时(2 分钟) | 用户关掉标签页就走,留一个开着的口 |
| 除本次检测所需之外不提供任何端点 | 最小面 |

## 检查项与它们的组合

| 项 | 靠什么 | 出网 |
|---|---|---|
| 谁占着默认路由(v4 / v6 各一条) | 本地 | 否 |
| IPv6 暴露 | 本地 | 否 |
| DNS 归谁 | 本地 | 否 |
| 公网出口(v4 / v6) | 浏览器 → 公共回声 | 是 |
| WebRTC srflx | 浏览器 → STUN | 是 |

**结论来自组合,单独任何一条都不是结论:**

- **WebRTC srflx ≠ HTTP 出口** → WebRTC 绕过隧道,真泄漏
- **v4 走 VPN 而 v6 出口是 ISP** → v6 泄漏(别的 VPN 最常见的漏洞)
- **默认路由归 X,而 DNS 解析器在 X 之外** → DNS 可能绕过

## 诚实性规则

这一节是整份设计里最要紧的,因为这个功能的失败模式不是崩溃,是**说一句好听的假话**。

- **三态,复用菜单已有的词汇**:`ok` / `bad` / `not checked`。**`not checked` 永远不
  计入异常** —— `MenuRows.swift` 已经这么写了(`anomalyCount` 只数 `.bad`),新代码
  只是接上,不是新发明。
- **绝不推断。** 页面被关掉、STUN 被挡、没网、第三方超时 —— 一律 `not checked`。
  **不许因为「没看到泄漏」就写 `ok`。**
- **`utun4` 必须翻成人话,翻不出就说翻不出。** `scutil --nc list` 给系统集成 VPN 的
  显示名;Tailscale / WireGuard / Mullvad 这类用户态工具按进程识别。认不出时显示
  **「无法识别的 VPN(utun4)」** —— **「无法识别」是一个合法答案,猜不是。**
- **每条结论都能展开看到它的依据**(接口名、路由、candidate、响应原文)。这是
  「小白看结论、老鸟展开」的落点,而且有第二个作用:**bx 判错时用户看得出它是怎么
  错的。** 一个不肯出示证据的检测工具,用户没有理由信它。
- **联网之前,页面先说要联系谁。** 公共回声端与 STUN 服务器的地址明写在页面上,
  不埋在代码里。

### 具体选哪几个第三方

**不在这份设计里钉死具体域名**,但选取标准是设计的一部分,计划照此选并写明理由:

- 回声端必须**同时有 v4-only 与 v6-only 的主机名**(否则问不出「v6 出口是谁」,
  而那正是别的 VPN 最常见的漏洞);
- 返回体要小且**格式稳定**(纯文本优先,别依赖 JSON 结构);
- **不用 china 列表里的域名** —— 这个项目已经在这上面栽过一次(拿
  `ifconfig.me` 当出口探测,而它本就在直连列表里,于是"漏直连"是自摆乌龙);
- STUN 用公共且长期稳定的一个即可,**只取 srflx,不做任何中继**。

**这些地址是用户可见的契约**,换它们等于换用户的暴露对象,所以必须是显式常量、
有测试钉住、且页面上照原样显示。

## 本期不做

- **菜单这一期只加一个入口项** `Check for leaks ↗`,除此之外一个字不动 ——
  尤其**不动 `Exit Location` / `IPv6 Leak` / `WebRTC` 那三行**,它们保持 `unknown`。
  往菜单搬结论是下一期的事,由这一期在真机上跑出来的数据决定搬哪些。
- **不留存任何结果。**
- **不做非 darwin。** 本地事实的原语只有 macOS 实现。
- **不驱动浏览器。** 只打开一个页面。驱动 Chrome 需要调试端口或辅助功能权限 ——
  一个安全工具去要那种权限,信任成本极高,而且换个浏览器就失效。打开页面拿到的
  结果完全一样,风险差一个数量级。

## 风险

**一、这个功能自己就是一个新的攻击面。** 一个「报告本机网络姿态」的 loopback 服务,
做砸了就是让任意网页读到用户的网络指纹。四道约束是硬要求,不是加分项,每一道都要有
自己的测试。

**二、恒绿的检查比没有更糟。** mDNS 那件事是个警告:一条永远说「没问题」的检查会把
整个界面训练成装饰。任何一项如果在真机上恒为 `ok`,要么它测错了东西,要么它不该存在。

**三、第三方暴露是用户明确接受的,但必须可见。** 用户点「检测」时把真实 IP 递给了
公共回声端和 STUN 服务器。缓解只有两条:**只在显式点击时发生**,以及**页面事先
明说要联系谁**。两条都不许省。

**四、全零 fixture。** 这个项目反复栽在这上面(上一期就有三条测试用了生产环境造不出
的输入)。一份空的浏览器上报必须产出 `not checked` 而不是 `ok`,这条要有独立测试并
变异验证 —— 否则「页面没跑成」会渲染成「一切正常」,而那正是最坏的那种失败。

## 测试策略

- **`internal/leakcheck` 是纯函数**:`(浏览器上报, 本地事实) → 一组三态结论`。
  表驱动,变异验证打在这里 —— 判据是这个功能唯一值钱的部分。
- **每一条组合规则各有一条测试**,删掉那条规则必须转红。
- **空上报 → `not checked`**,独立测试 + 变异验证(见风险四)。
- **本地服务的四道约束各一条测试**:无 token 被拒、错 Origin 被拒、用过即关、超时即关。
- **JS 保持愚蠢**:只采集、只回传、只渲染 Go 给的结论,一个判断都不做。约束靠结构
  保证 —— 页面拿到的就是最终结论文本,没有可判断的原料。
