# 死规则 —— 跨重启累计,才敢说「这条从来没命中过」

## 它补的是哪个洞

「规则体检」(`docs/superpowers/specs/2026-08-17-rule-review-design.md`)四条检查里,
第 1、3 条已实现(危险规则、两类冗余 + 被反向压住的失效规则)。**第 2 条(死规则)
一直没做,因为它是唯一需要新增持久化的一条。**

`stats` 今天已经按规则记 `{attempts, failures}`(`RuleOutcome`,键
`ruleKey{source, rule}`)。一条 `attempts` 恒为 0 的用户规则,要么域名早就不用了、
要么写错了。但**计数在 Core 重启时清零**,所以「0 次」只说明「本次运行没命中」。

原 spec 自己写下了这条警告:

> 判据必须跨重启累计,否则会把刚重连的机器上每一条规则都报成死的 —— 那是这个
> 项目最忌讳的那种假阳性。

## 判据:双门槛,三个都要满足

一条用户规则被判「死」,必须同时满足:

1. 它在累计历史里的 `attempts` **恒为 0**
2. Core **累计运行 ≥ 14 天**
3. 全局**累计判定 ≥ 20,000 次**

**为什么两个门槛而不是一个。** 只看时长,一台开着却几乎不上网的机器会把全部规则
报成死的;只看总量,一次大流量突发就能让门槛很快达到,而那段时间里一条季节性规则
本来就不该被命中。两个门槛各自堵住对方的失效模式。

**数值依据取自这台机器的真实量级**:一次运行里 `direct 26186`(CLAUDE.md 记的
真机数据),而 UDP 那批反事实计数「样本约 150 条」是几小时的量。14 天足够跨过
「这周没用那个服务」,20,000 次判定确保机器真的被用过、而不是开着挂机。
**这两个数是可调的一行**,不是设计的承重部分。

### 「没有条目」不等于「attempts == 0」

`stats` 有 `maxTrackedRules = 256` 上限,超出之后**新键不再被记**。所以一条规则在
累计表里**没有条目**有两种可能:它从没被命中过,或者它从没被跟踪过。

**两者必须分开,判「死」只认前者。** 把「没跟踪」读成「没命中」,正好在规则最多、
最需要体检的那台机器上产生最多假阳性。做法是持久化里显式记下「这一版的跟踪上限」
与「是否曾经溢出」,溢出过就把死规则这一类整个标为**没查**(见下)。

### 跨版本累积要说出来

历史跟着**规则**走,不跟着二进制走 —— 规则没改,证据就仍然成立。若不这样,频繁
升级的机器永远达不到双门槛,**这个功能就静默地从不生效**,而那是这个仓库反复出现
的失效形状。

**但跨了几个版本要报出来。** 一条规则跨 6 个 bx 版本累积到 14 天,而其中某个版本
改过路由判定 —— 那份「从未命中」的证据比在单一版本下累积的弱。持久化里记下累积
跨过的版本集合,结论里说出来,**让用户自己打折**。

这与本仓库已有的纪律同源(`BuiltinListChecked` / `BuiltinSkipReason`、
`internal/observe` 的三态):**用户必须能判断一个结论可不可信。**

## 持久化归 Core,不牵 Guardian

**Core 已经在往 `/var/lib/bx` 写盘**(`internal/supervisor/refresh.go` 的
`atomicWriteFile`,以及 PID 文件),所以这份历史完全可以由 Core 自己持有。

**这一点推翻了原 spec 里的一个顾虑。** 原文担心「`stats.Counters` 在 Core,而唯一的
持久化范例由 Guardian 的调谐环驱动,Linux/Windows 没有 Guardian」—— 那个障碍只在
**非要照抄那个范式**时才成立。Core 自己写,就没有平台缺口。

**信封形状照 `internal/guardian/throughputhistory.go`**:`schema_version`
(未知版本一律当空并报错,不做迁移)、原子替换、带时间戳。那个文件已经趟过这一套。

存这些:

| 存什么 | 为什么 | 容易做错的地方 |
|---|---|---|
| 每规则 `{attempts, failures}`,键 `ruleKey{source, rule}` | 判据主体 | — |
| **累计 Core 运行时长** | 门槛 2 | **是 Core 累计在跑的时长,不是「距首次见到这条规则过了多久」。** 后者好实现得多,但它把 Core 没在跑的时间也算进去 —— 而那段时间里任何规则都不可能被命中,拿它当分母是把门槛悄悄降低 |
| **全局累计判定总数** | 门槛 3 | **数的是全部判定,含内建列表命中**(`RuleAttempt` 的每一次调用)。它衡量的是「这台机器有没有真的被用过」,不是「用户规则被用过几次」—— 只数用户规则会让一台流量全走内建列表的机器永远达不到门槛 |
| 累积跨过的 bx 版本集合 | 结论要说出来,让用户打折 | — |
| 那一版的跟踪上限,与**是否曾经溢出** | 「没有条目」≠「attempts == 0」 | 溢出过就整类标「没查」 |

### 加载时按当前配置清掉孤儿

`rule` 是**配置里那一行的原文**。用户把 `*.qq.com` 改成 `*.qq.cn`,旧键就成了孤儿。

**Core 起来读盘时,把不在当前 `rules` 里的条目直接丢掉。** 于是盘上永远只有当前
规则的历史,`maxTrackedRules` 不会被孤儿吃掉。代价是**改回去的规则要重新累积** ——
接受,因为另外两种做法(冻住不推进、带过期时间)都要再加一层淘汰或第二个时间常量,
而这个功能已经有一个时间常量了。

### 写盘节奏:周期 + 干净关闭,而不能只靠后者

照 `refresh.go` 已有的周期性工作加一拍(几分钟一次),**外加干净关闭时再写一次**。

**不能只靠干净关闭**:launchd 会 SIGKILL Core(CLAUDE.md 记着这件事打断过 defer),
那时最后一段累计会丢。周期写保证丢的量有上界。

## doctor 怎么拿到这些数:经控制 socket,不读文件

**不让 `bx doctor` 直接读那个文件。**

`/var/lib/bx` 是 `drwx------ root`(实测),而文件本身 0644 —— 也就是说
`sudo bx doctor` 读得到、`bx doctor` 读不到。直接读文件会立刻重演 china 列表刚修完
的那个分裂(见 `2f3d273`)。

而 Core 的控制 socket 是 **0666**(非 root 可读,`bx status`/`bx mcp` 都靠这一点),
`bx status` 已经从它拿 `rules[]`。**这份历史走同一条路。**

**累计值必须与本次运行的计数分开发布,不合并成一个数。** 原 spec 的警告
(「0 次只说明本次运行没命中」)正是靠这个区分才有着力点;混成一个字段,那句警告
就失去了对象。所以控制面发布的是两组数:本次运行的 `rules[]`(已有),与累计历史
(新增),字段名各自自明。

**Core 不在跑时,死规则这一类是「没查」而不是「零条」** —— 与 `BuiltinListChecked`
同一条纪律。同理,历史读不出来、schema 不认、或跟踪上限溢出过,都是「没查」并说明
理由。

## 判据住哪儿

`internal/rulereview` 是**纯判据包**,有 AST 纯度守卫(禁 `os`/`net`/`os/exec`,
internal 依赖只许 `route` 与 `policy`)。**这条判据也进那里**:`Input` 多一个字段
承载「每规则的累计计数 + 两个门槛的当前值 + 版本集合 + 溢出标志」,I/O 全留在
`internal/cli`。**不许为此放宽纯度守卫。**

`Report` 多一个 `DeadCount`,**与既有四个计数并列、永不相加**(原 spec 的
Global Constraint)。

## 非目标

- **不自动改配置。** 只报告 —— 与原 spec 一致,而且改完要重连(bx 不热重载)。
- **不做第 4 条(缺失规则)。** 它依赖同一套数据,但 spec 自己说「最容易变成噪声,
  门槛要比前三条严得多,宁可不说」,单独决定。
- **不给内建列表计数。** 内建列表里没有哪一行可点名、用户也改不了(与
  `stats.ruleWorthReporting` 同一条纪律)。
- **不做主动探测。** 判据只用已经发生的流量。
- **不改 `stats` 的现有 JSON 字段。** `bx status --json` 是被消费的契约。

## 已知会成为问题、但本设计不解的

- **一条规则可以合法地闲置很久。** 14 天挡住了「这周没用」,挡不住「这台机器一年只
  出差用两次那条规则」。双门槛把假阳性压低,不是压成零 —— 而这一类的产出是**建议**,
  不改变任何流量去向,所以代价可控。
- **升级换二进制之后,「什么算命中」可能变了。** 版本集合把这件事说出来,但不代替
  判断 —— 谁改了路由判定,就该知道旧的零计数弱了一档。
- **`maxTrackedRules = 256` 本身没动。** 溢出时整类标为「没查」,而不是提高上限 ——
  提高它要先知道真机上有没有人接近过那个数,而今天没有这个数据。

## 前置工作

无。`stats` 的按规则计数、Core 的落盘原语、控制 socket 的发布通道、
`internal/rulereview` 的纯判据结构,四样都已经在那里。
