# bx 集成台设计 —— 让静默失败变响亮

## 为什么

2026-08-09 一轮多服务器开发结束后的统计:

| | |
|---|---|
| 控制面 : 数据面 生产代码 | **28,904 : 3,088 = 9.3 倍** |
| `Run()` 函数长度 | **578 行**(组装根) |
| 真跑系统的集成测试 | **3 个**,且只测原语:快照往返、死手回滚、netconf 往返 |
| 本轮复审抓到的 finding | **11 个**,其中 6 个可追到设计而非实现 |

数据面本轮 **0 bug**。所有 bug 都在那 9.3 倍里,而且 **Task 6 的两个 Critical 都住在
`Run()` 的六行接线上**——抽出来的每个单元都守得严严实实,复审做三个变异全绿。

### 一句话诊断

**这个代码库没有落脚点。** 组装根不可测,于是「逻辑对」和「接线对」是两件事,
而所有事故都在后者。补救手段是读源码文本/AST 的守卫——本轮被绕过 **8 次**
(拼写而非身份、邻近注释满足、行为等价的重实现、看起来像缓存优化的重赋值……)。
**用文本去守编译器和测试本该守的东西,天然是漏的。**

第二条同样致命:**失败是静默的**。一个错的 bypass 集合产生的信号是——没有信号。
隧道连得上、`bx status` 显绿、流量绕圈或泄漏。Task 6 里每一个 bug 都**由构造决定**
是静默的,所以只能靠人去想到它。

## 这个台子是什么

**在一个临时 netns 里跑真正的 `supervisor.Run()`,做一次真实的服务器切换,
然后去问内核:路由表、策略规则、屏障开口现在到底是什么样。**

不是新造一套。它长在现有 netns 基建上(`hijack_netns_linux_test.go` 那套
`unshare(CLONE_NEWNET)` + 锁 OS 线程 + `//go:build integration && linux` + root,
CI 已在跑 `sudo go test -tags integration`)。差别是:现有三个测的是**原语**,
这个测的是**流程**。

## 唯一的生产代码改动:给 `Run()` 开一道缝

今天 `buildTunnel` 是 `Run()` 内部的闭包(`run.go:163`),`Options` 没有任何注入点。
**这本身就是「没有落脚点」的具体形态**——想跑 `Run()` 就必须真的拉起 brook/sing-box
子进程、真的连一台远程服务器。

```go
type Options struct {
    // …既有字段不动…

    // BuildTunnel 可选:替换建隧道的方式。nil = 生产默认(拉起 brook/sing-box 子进程)。
    // 存在的理由是集成台要在 netns 里跑完整 Run() 而不发任何真实外网流量;
    // 它是本代码库唯一一处「组装根可以被外部指定」的缝。
    BuildTunnel func(link, recoveryID string, auxiliaryHTTP bool) (*tunnel.Tunnel, error)
}
```

`nil` 时行为与今天**逐字节相同**——这一点由「既有测试零改动」来证明。

假隧道在包外可直接构造,因为 `tunnel.New(socksAddr, RunnerFactory, HealthCheck)`
本就是导出的:进程内 socks5 服务端 + 空 `Runner`(`Wait`/`Kill` 两个方法)+
立即返回健康的检查。**不拉任何子进程,不发任何外网包。**

### 为什么不注入平台

不注入。`platform_linux.go` 的 fdbased TUN + SO_MARK + `ip rule` 策略路由在 netns 里
就是真的跑——**那正是要测的东西**。注入平台等于把被测对象换成桩,回到今天的处境。

## 台子断言什么

优先钉住 Task 6 五轮修复里**永远无法自证**的那几条:

1. **启动后的 bypass 覆盖**:清单里**每一台**服务器的**两条**链接对应的 IP,
   都真的在内核路由表里有 bypass 条目。少一条 = 隧道自己的流量被劫进 TUN = 成环。
2. **已知服务器之间切换不动路由**:切换前后 `ip route show table 100` 与 bypass
   条目集合完全相同,且切换成功。这是「启动时全铺好」那条设计的唯一实证。
3. **点名目标解析失败必须拒绝切换**:`/v0/server` 指向一台解析不出 IP 的服务器,
   必须 500,且**仍在原来那台上**——而不是在 bypass 没落实的情况下切过去。
4. **屏障开口等于当前服务器**:切换后 `RuntimeState.ServerBypass` 只含当前那台的
   传输服务器地址,不含用户 `hosts:` 覆盖、不含上一台。这条走过五轮修复、三次翻车。
5. **退出干净还原**:`ip rule list` 回到基线,一条不多一条不少。

前四条今天全部只有单元测试与源码守卫背书;第 5 条现有 netns 测试只覆盖了
`netConf` 这一层,没覆盖 `Run()` 的完整 defer 链。

## 这个台子替换掉什么

**`internal/supervisor/runwiring_ast_test.go` 里那两条 AST 接线守卫应当降级或删除。**
它们存在的唯一理由是「接线不可测」;台子跑起来之后,接线由真实行为钉住,
而 AST 守卫是**更弱**的替代品(本轮被绕过 8 次)。

保留哪些、删哪些,由台子建成后逐条判断——**能被台子覆盖的就删掉**,
留下来的每一条都要说明台子为什么覆盖不到它。

## 本期不做

- **不测真实隧道协议**。reality/hysteria2 的握手已有真机 e2e 背书(2026-06~07),
  不重复。台子测的是控制面。
- **不发任何真实外网流量**。netns 里没有外网,断言只看内核状态。
- **不覆盖 macOS 与 Windows**。netns 是 Linux 概念。**macOS 的路由/DNS/屏障仍然
  只能真机验证**——这一点必须说清楚,否则台子会给人一种虚假的安全感:
  bx 的主要用户平台恰恰是台子照不到的那个。
- **不做性能/吞吐测试**。

## 已知取舍

**台子在 Linux 上验的是「控制面逻辑对不对」,不是「macOS 上路由语义对不对」。**
两者都会出事,但形状不同:前者是我这一轮反复踩的(冻结副本、顺序反了、
从错的地方派生),后者是平台语义差异(`route -n get` 的输出、`networksetup` 的行为)。
台子只解决前者,而前者恰好是本轮 11 个 finding 的绝大多数。

**注入缝本身是风险**:`Options.BuildTunnel` 非 nil 时走的是与生产不同的路径。
缓解是——nil 分支必须与今天逐字节相同,由既有测试零改动证明;且台子**只**替换建
隧道这一件事,平台、路由、DNS、屏障全部走生产代码。

## 测试策略

台子自己也要被验证——一个测不出 bug 的集成测试比没有更糟(它给人安全感)。
**每一条断言都要用变异证明它会红**:

- 把 `bypassLinks` 改成只返回当前那台 → 断言 1 必须红
- 把切换路径改成先换传输再装路由 → 断言 2 必须红(路由集合会变)
- 把「刷新失败仍继续切」放回去 → 断言 3 必须红
- 把 `store.set` 的后两个实参写反 → 断言 4 必须红
- 去掉 `Run()` 的某一段 defer → 断言 5 必须红

**这五个变异正是本轮五轮修复里真实发生过的 bug。** 台子必须一个不漏地抓住它们,
否则它没有存在的理由。

## 风险

**最大的风险是台子建起来之后没人再看真机。** macOS 是主平台,而台子照不到它。
缓解:CI 里台子的名字与失败信息必须写明它只覆盖 Linux 控制面;`CLAUDE.md` 的
「真机未验」清单不因台子存在而清空。

**第二个风险是台子很慢或很脆,然后被人加 `-short` 跳过。** 缓解:台子必须在
单次 `sudo go test -tags integration` 里跑完且不依赖外网;CI 已有断言「netns PoC
真跑过(PASS 而非 SKIP)」的先例(`ci.yml:115`),新台子沿用同一手法。
